# Scope Discipline — 무관 코드 건드리지 마라 / 없앤 걸 되살리지 마라

> **P1 규칙 (2026-07-07 제정)**. 근거: 사용자 명시 반복 불만 —
> "약봉투 이름 표시 작업이 복약 체크를 망가뜨렸고, 체크 복구하면서 없앴던 시간제약을 다시 넣었다."
> 한 작업이 **무관한 기능을 깨뜨리거나**, **사용자가 의도적으로 제거한 것을 되살리는** collateral regression 을 금지한다.

## 1. 최소 diff 원칙 (touch only the spec)
- 작업은 **spec 이 명시한 것만** 변경한다. 옆의 코드가 "개선 가능해 보여도" 손대지 않는다.
- 표시(label) 작업이면 표시만. **동작(체크)·검증·상태전이 로직은 건드리지 않는다.** 같은 파일/화면이어도 무관 부분은 그대로 둔다.
- 리팩터·정리·"이왕 하는 김에"는 spec 에 없으면 금지. 하고 싶으면 CTO 에 별도 제안.

## 2. 없앤 기능 되살리기 금지 (anti-revival)
- **새 제약·검증·가드·기본동작을 spec 없이 추가하지 마라.** 그것이 과거 의도적으로 제거된 것일 수 있다.
  - 실제 사례: 복약 체크 시간제약은 커밋 `0eae70c`("시간 경계 완화")로 **의도적으로 없앤 것**. 이를 다시 넣으면 regression.
- "이게 맞는 것 같아서" 검증을 추가하기 전에: git log/blame 으로 **과거에 제거된 이력이 있는지** 확인. 있으면 절대 재추가 금지.
- 판단 안 서면 추가하지 말고 CTO 에 질문. **기본값은 "덜 제약한다".**

## 3. Regression 체크 (변경한 화면/모듈의 핵심 동작 재확인)
- 어떤 화면/모듈을 수정하면, 그 화면의 **주요 상호작용이 여전히 되는지** 확인 후 DONE.
  - 홈 표시 바꿈 → **홈 복약 체크 여전히 되는지** 탭 테스트.
  - 등록 흐름 바꿈 → 등록→오늘 체크 여정 e2e.
- verification-evidence.md 의 "핵심 여정 끝까지 e2e" 와 연동. 표시 1줄 바꿨다고 체크가 깨지면 안 된다.

## 4. 동시 편집 충돌 방지 (CTO)
- **같은 파일을 건드리는 태스크를 동시에 여러 개 굴리지 마라.** (예: search.tsx 에 조회전용+최근검색+... 병렬 → 반쯤 깨진 번들, transient 오류).
- 같은 파일/화면 관련 작업은 **직렬화**. 한 태스크 DONE + 검증 후 다음.
- 여러 패널이 겹치는 영역을 만지면 CTO 가 순서를 정해 하나씩.

## 5. 검증 시 stale/mid-edit 구분
- 사용자가 "안 된다"고 하면, **코드에 실제 원인이 있는지 먼저 확인**(grep/diff). 코드에 없으면 stale bundle·mid-edit·no-op 가능성 → 추측으로 고치지 말고 재현·클린빌드 후 재확인 or 사용자에 정확한 증상 질문(짐작금지).
- 실제 사례: "12:30 시간제약"은 코드에 없었고 transient 였음. 코드 조사 없이 시간제약 코드를 넣었으면 **없던 버그를 만들 뻔**.
