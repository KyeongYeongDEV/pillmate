## Pressable function-style 이 렌더에 무시됨 (2026-07-06)
- **문제**: 버튼 minHeight/padding 커밋 3개가 렌더에 한 번도 적용 안 됨 (20dp 고정)
- **접근**: ①번들 curl→새 코드 확인 ②lsof 로 Metro 연결 확인 ③스크린샷 픽셀 실측 → "코드는 신선한데 렌더만 옛날" = 라이브 버그 확정 ④function-style→정적 style + 높이를 outer View 로
- **판단 질문**: stale bundle 로 단정하지 않았다 — 번들 내용을 직접 확인해 배제. 반대로 "커밋됐으니 적용됐겠지"도 배제(픽셀 실측)
- **재사용 규칙**: "UI 변경이 안 보인다" → ①서빙 번들 grep ②픽셀 실측, 그 다음에야 코드 수정

## docker compose config 가 실키를 노출 (2026-07-06)
- **문제**: CICD 검증 중 GEMINI/OPENAI 실키가 로그에 노출
- **접근**: compose 는 `--env-file` 생략 시 기본 `.env`(실키) 자동 로드 → `${VAR}` 치환에 실값 렌더
- **판단 질문**: "config 는 읽기 전용이라 안전"이 함정 — 렌더 출력 자체가 노출 경로
- **재사용 규칙**: compose 검증은 반드시 더미 `--env-file`(SENTINEL 값) 명시

## 당일 등록 처방전 체크 불가 (2026-07-06)
- **문제**: 홈 체크 탭 무반응 — FE 는 건전, dose_logs 가 없어서 no-op
- **접근**: FE→API→DB 순서로 내려가며 각 층 실측 (탭 핸들러→curl 200→해당 처방전 dose_logs 0건) → 등록은 스케줄만 만들고 dose_logs 는 야간 배치 전용이 근본원인
- **판단 질문**: "체크 API 가 고장"을 배제 (curl 로 다른 dose_log 는 200) — 증상 지점이 아니라 데이터 부재 지점을 찾음
- **재사용 규칙**: "탭해도 무반응" → 핸들러가 조용히 return 하는 가드(빈 배열 등)부터 의심, 데이터 존재를 DB 에서 확인

## 소켓 /clear 가 실행되지 않음 (2026-07-07)
- **문제**: cmux send-panel 로 보낸 /clear 가 idle 패널에서도 실행 안 됨
- **접근**: Return/인라인 \r/Escape 후 Enter 전부 시도 → 슬래시 자동완성 메뉴가 Enter 를 소비함이 원인. 대안 = 프로세스 재시작(restart-panel: Ctrl-C 2회→동일 런치커맨드 fresh 재기동)
- **판단 질문**: "Enter 미전달"로 단정 안 함 — 일반 텍스트+Enter 는 정상 동작함을 확인해 키 전달 자체는 배제
- **재사용 규칙**: 패널 하드 리셋은 `bin/restart-panel <role>` 만 신뢰 (소켓 슬래시 명령은 자동완성에 막힘)

## 시퀀스 desync 로 신규 유저 INSERT 실패 (2026-07-06)
- **문제**: 카카오 첫 로그인에서 users_pkey 중복 — 시드가 명시 id 로 들어가 시퀀스가 1에 멈춤
- **접근**: 에러의 제약명(users_pkey)→시드 테이블 last_value 조회→setval(max(id))
- **판단 질문**: 코드 버그로 단정 안 함 — upsert 로직은 정상, DB 상태 문제
- **재사용 규칙**: 시드 넣은 테이블은 배포 전 전 테이블 `setval(seq, max(id))` 일괄 점검 (deploy-gate G4)

## 시간 예산이 실패 제조기가 된 사건 (2026-07-11)
- **문제**: OCR 지연 개선용 per-call 20s 상한이 실사용자 요청을 20.0s에서 잘라 504 (정상 소요 17-18s)
- **접근**: 관측 로그(vision_attempt outcome=timeout, elapsed 20012/3488)로 즉시 원인 특정 → 상한 30s + 잔여예산<정상소요면 재시도 스킵 + 총예산 45s로 재튜닝
- **판단 질문**: "30초 목표"를 상한으로 직역하지 않았어야 — 목표는 p95이지 하드컷이 아님. 잔여 3.5s 재시도처럼 성공 불가능한 시도는 예산 낭비
- **재사용 규칙**: 타임아웃 상한 = 정상 p95 × 1.5 이상. 재시도 전 "잔여예산 ≥ 정상소요" 가드 필수
- **최종 결론(2026-07-12)**: 성능 목적의 시간 예산 자체를 폐기 — 사용자는 기다려서 성공하는 걸 선호. 남기는 건 행 방지 안전망(체인 상류 타임아웃보다 안쪽) 하나뿐. 재시도는 에러 기반만. "타임아웃은 성능 장치가 아니라 안전망"
